## 3. 原始命令与执行序列

以下是历史命令，供定位，不应直接当作下一步自动执行脚本。

```bash
lerobot-setup-motors --teleop.type=so101_leader --teleop.port=/dev/ttyACM0
sudo chmod 666 /dev/ttyACM0
lerobot-setup-motors --robot.type=so101_follower --robot.port=/dev/ttyACM0
```

| 顺序 | 操作/观测 | 写入与状态判断 |
| --- | --- | --- |
| A | Leader 首次：`PermissionError: [Errno 13] Permission denied`，包装为 `ConnectionError` | 打开串口失败，无 ID 写入；不能把最终通用连接提示误判为端口不存在 |
| B | 用户执行 chmod 后 Leader 完整成功 | 六个成功输出，正常返回提示符 |
| C | `ls /dev/ttyACM* /dev/ttyUSB* 2>/dev/null` | 只输出 `/dev/ttyACM0`；这只是当时设备可见性 |
| D | 再次 chmod；Follower 到 wrist_flex 等待处 Ctrl+C | gripper=6、wrist_roll=5 成功；未进入 wrist_flex 设置 |
| E | 重跑 Follower，同位置 Ctrl+C | 与 D 相同；没有全局回滚机制的迹象 |
| F | 重跑 Follower，前三颗成功，elbow_flex 查找失败 | `RuntimeError: Motor 'elbow_flex' (model 'sts3215') was not found. Make sure it is connected.`；失败原因未查明 |
| G | 最后一轮 Follower 六颗全部成功 | 包括 elbow_flex=3；原失败未复现，不足以确认是线缆、电源还是连接顺序造成 |

## 4. 已解决问题与推理边界

### 4.1 重跑是否使 ID 累加或出现两个地址

本聊天先前核对过上游 `MotorsBus.setup_motor`：发现当前单颗电机，读取其现有通信设置，再写配置目标 ID 和波特率。ID 是被覆盖的寄存器值，不是历史分配列表。历史上游参考：<https://github.com/huggingface/lerobot/blob/main/src/lerobot/motors/motors_bus.py>。这是当时的机制核对，本次没有重新拉取；`main` 可变，不能替代用户 Ubuntu 安装版本证据。

因此“同一颗电机 5 → 4”本身已解释清楚。真正仍需证据的是物理设备身份：程序按提示指定目标地址，不能知道用户手中拿的是哪颗关节电机。若两颗电机最终同为 4，或 ID 5 电机实际装错关节，成功打印不足以发现。

### 4.2 中断与恢复

本日志中的两个 Ctrl+C 均在输入等待处，与写寄存器过程中断不同，不能泛化为所有中断都无影响。最后完整重跑覆盖了此前未完成步骤；不应仅因历史中断而再要求用户重复写 EEPROM。

### 4.3 串口权限与角色

chmod 对当时设备节点生效，不证明 USB 重插或重启后权限持久。ACM 数字表示枚举名，不是设备角色；角色识别必须依赖逐板观察或稳定身份信息。官方单颗连接流程的历史参考：<https://huggingface.co/docs/lerobot/en/so101>。

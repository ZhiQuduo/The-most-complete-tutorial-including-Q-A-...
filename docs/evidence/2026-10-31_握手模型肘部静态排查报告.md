# 握手模型肘部问题静态排查报告

日期：2026-10-31  
范围：`D:\具身智能` 工作区；不再执行硬件动作，不修改电机、校准、PID 或停止阈值。

## 结论

现有证据不支持“肘部电机或基础遥操作链路故障”。用户已确认标准遥操作中肘部可以正常运动；项目内的只读寄存器记录也显示 ID 3、型号 777、位置模式、状态 0、力矩上限 1000、温度 27 摄氏度、12.0 V，未见硬件错误码或持续过载证据。

握手链路的主要问题在软件契约没有闭合：训练数据使用的是数据集原生坐标，当前握手单轴执行入口却强制把观测转换成 `RANGE_M100_100`，再把模型输出按同一假设转换回本地角度。代码同时明确标记 `state_action_convention_verified=False` 和 `physical_handshake_validated=False`，因此这条坐标转换链不能被当作已验证的物理目标链路。肘部试动的失败更像“模型坐标/零位契约未证实 + 专用执行器过严”的组合问题，而不是肘部本身不能动。

## 证据链

### 1. 基础硬件与标准遥操作

- `logs/elbow_register_diagnostic_20261030_152331.json`：肘部 ID 3，型号 777，`Operating_Mode=0`，`Status=0`，`Torque_Limit=1000`，`Max_Torque_Limit=1000`，温度 27，电压 120（SDK 原始单位），`Present_Load=0`、`Present_Current=0`；三次读数一致。
- `docs/evidence/2026-10-30_ssh只读验证.md`：记录了肘部可通信、静态读数正常，并明确说明静态诊断不能还原此前上力试动时的跟踪异常。
- 用户本轮确认标准遥操作中肘部能动。该证据直接把“端口/ID/总线/电机完全不能动”排除在当前首要根因之外。

### 2. 模型训练坐标与运行时坐标不一致风险

- `握手Demo/dataset_info.json:17-39` 的动作和状态均是六维 `*.pos` 特征；`握手Demo/reference_check.json:5-27` 的训练状态和动作包含 `-99`、`96`、`63` 等数据集原生数值。
- `握手Demo/checkpoint/config.json` 使用 ACT 的 `MEAN_STD` 预处理/反处理；模型服务会先把请求状态交给 checkpoint 的 normalizer，再把输出 unnormalize 回训练数据坐标。服务并没有在模型内部声明“输入必须是 RANGE_M100_100”。
- `握手Demo/recheck_saved.py:26-40` 自定义了角度与 `RANGE_M100_100` 的换算；该函数只是坐标假设，源码注释也写明“不是跨机器人校准一致性的声明”。
- `握手Demo/joint_trial.py:22-35` 和 `握手Demo/wrist_trial.py:22-35` 却强制要求来源记录的 `model_input_convention` 为 `range_m100_100`，并在请求前执行 `convert(..., True)`。这与参考训练行显示的数据集原生坐标形成直接风险点。
- `握手Demo/probe_server.py` 的响应字段仍写着 `state_action_convention_verified: False`、`physical_handshake_validated: False`；`握手Demo/reference_check.json` 也明确写着单位是 dataset native coordinates、不是本地物理角度。

因此，当前代码能够生成有限、形状正确的六轴预测，不等于预测已经转换成了本机肘部的正确目标。尤其是肘部接近校准范围边界时，重复归一化/反归一化会把小误差变成实际目标方向或幅度误差。

### 3. 肘部试动日志与执行器行为

- `logs/elbow_controlled_test_20261030_152501.json` 中请求变化为 `+1.0` 度，起点肘部 `96.7912` 度，保存目标 `97.7912` 度。
- 38 个采样行中，反馈最高只到 `96.8791` 度；最后若干行仍是目标约 `97.7582`、反馈 `96.8791`，残差约 `0.879` 度。
- 同一文件却写入 `status: "completed"`、`error: null`。这与“目标误差在 0.4 度内并稳定 0.5 秒”的执行器完成条件不一致，说明该日志的完成状态不能作为“肘部完成了 1 度动作”的证据。
- `握手Demo/handshake_motion_core.py:236-250` 会按 `LEAD * 0.75` 检测持续跟踪偏差；`握手Demo/joint_motion_guard.py` 又把试动轴限制为最多 1 度、其他轴最多 0.5 度。该保护逻辑可能在目标尚未真正到达时中止，但它不会制造电机无法运动；它只会把“未达到目标”报告为失败或停止。

## 根因判断

按证据强度排序：

1. **高可信：握手执行入口的模型坐标契约未验证。** 训练样本和参考预测是原生坐标；单轴入口强制使用 `range_m100_100`，服务和报告又明确标记该约定未验证。这是代码层面可直接定位的缺陷。
2. **高可信：当前肘部失败被专用执行器的跟踪阈值放大。** `LEAD=0.8` 时，连续误差阈值只有 `0.6` 度；日志反馈只变化约 `0.088` 度，却持续发送目标，容易触发保护。该机制解释了“遥操作能动、握手试动失败”的表象差异。
3. **中可信：模型首帧本身不是物理可执行目标。** 参考文件明确写明单次训练观测、不是独立评测，也未完成物理握手验证。不能把模型输出误认为正确的本机肘部角度。
4. **低可信/未证实：机械卡滞、死区、负载或 PID 故障。** 当前只读寄存器正常，且标准遥操作能动；现有证据不足以支持这些作为首要根因。

## 已排除或不能据此认定的事项

- 不能认定“握手模型已经验证正确”：服务只验证了 checkpoint 加载、输入输出形状和有限数值。
- 不能认定“肘部已完成握手动作”：模型服务 `motion_enabled=false`，现有日志也没有完整握手执行记录。
- 不能把 `status=completed` 当作动作成功；该字段与采样反馈矛盾。
- 不能据此修改 PID、死区、力矩上限、校准或删除跟踪保护。

## 结束状态

本次静态排查已完成。结论是：肘部问题首先应归因于握手模型运行时的坐标/校准契约未闭合，以及单轴试动执行器对小幅跟踪误差的严格中止；没有足够证据把问题归因于已被标准遥操作验证可运动的肘部硬件。后续若重新验证，唯一有意义的方向是先用同一 checkpoint 的训练原生坐标完成离线 A/B 对照，再单独验证模型输出到本机角度的映射；不应继续通过放宽阈值来“凑通过”。
